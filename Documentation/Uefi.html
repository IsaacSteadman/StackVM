StackVM UEFI / EFIAPI ABI (Workstream D1b.2, part of E1)

This page specifies how UEFI firmware and UEFI applications run on StackVM: the EFIAPI calling convention, the EFI_SYSTEM_TABLE / Boot-Services / Runtime-Services table layouts, the image entry handoff efi_main(ImageHandle, SystemTable), the GUID / handle / protocol model, the EFI memory-map descriptor format, and the ExitBootServices / event / TPL semantics. It is the contract that the (separately-built) UEFI firmware (D1b.4) and any EFI application / EFI-stub kernel target. The image container format — PE32+/COFF with a .reloc base-relocation table — is specified separately alongside the toolchain (workstream D1b.1, pe_file.py); this page only references it.

The design follows the UEFI 2.x specification field-for-field so a stock EFI-stub or GRUB-as-an-.efi sees the layouts it expects; the only StackVM-specific parts are (a) the calling convention (StackVM is a stack machine, not x86-64), (b) the firmware/device backends (D1b.3/D1b.4, which map onto the D2–D5 interrupt / timer / device substrate), and (c) the use of a devicetree configuration table (pairing with D1a) instead of ACPI/AML.

The EFIAPI calling convention

On real hardware EFIAPI pins UEFI to the Microsoft x64 register convention. StackVM has no general-purpose registers, so on StackVM EFIAPI is the native StackVM C calling convention — the same one the compiler emits for an ordinary C call (see CALL/RET). A port that marks a function EFIAPI (or __attribute__((ms_abi)), accepted and ignored) gets exactly the standard ABI:

  • Argument passing. Arguments are pushed by the caller, right-to-left, so the first argument ends up nearest the call frame and is reached at the lowest positive offset from the callee's base pointer. Each UINTN/INTN, pointer, EFI_HANDLE, EFI_STATUS and BOOLEAN argument occupies one 8-byte stack slot; smaller integers are widened to 8 bytes. Structures larger than 8 bytes are passed by reference (the caller materialises a copy and passes its address), matching UEFI usage where aggregates are always passed via pointer.
  • Return value. The caller reserves the return slot below the arguments (an ADD_SP of the return size) before pushing arguments; the callee writes the result there. UEFI functions return EFI_STATUS (an UINTN, i.e. a 64-bit value), so the return slot is 8 bytes.
  • Frame + cleanup. CALL pushes the previous base pointer and the return address and sets bp = sp; RET restores them. The caller pops the argument area (an RST_SP of the total argument size) after the call returns — the return slot it allocated survives. This is a caller-cleanup convention, so variadic EFI services (e.g. ConOut->OutputString style helpers built on it) work without callee knowledge of the argument count.
  • Status encoding. EFI_STATUS is an UINTN; an error sets the high bit (bit 63 on the 64-bit StackVM), a success or warning clears it. EFI_SUCCESS = 0; common errors are EFI_LOAD_ERROR = 0x8000000000000001, EFI_INVALID_PARAMETER = 0x8000000000000002, EFI_UNSUPPORTED = 0x8000000000000003, EFI_BUFFER_TOO_SMALL = 0x8000000000000005, EFI_NOT_READY = 0x8000000000000006, EFI_NOT_FOUND = 0x800000000000000E.

Every table is prefixed by an EFI_TABLE_HEADER (24 bytes): Signature (UINT64), Revision (UINT32), HeaderSize (UINT32), CRC32 (UINT32), Reserved (UINT32). Revision carries the UEFI revision (e.g. 2.70 = (2<<16)|70); the firmware computes CRC32 over the whole table with the field zeroed.

EFI_RUNTIME_SERVICES

EFI_TABLE_HEADER (Signature 0x56524553544e5552 "RUNTSERV") + 8-byte EFIAPI pointers, spec order: GetTime, SetTime, GetWakeupTime, SetWakeupTime, SetVirtualAddressMap, ConvertPointer, GetVariable, GetNextVariableName, SetVariable, GetNextHighMonotonicCount, ResetSystem (and 2.x additions UpdateCapsule, QueryCapsuleCapabilities, QueryVariableInfo). GetTime is backed by the D5 RTC; the Get/SetVariable family is backed by NVRAM variable storage (host-file / block region, D1b.3). Runtime services remain callable after ExitBootServices; once the OS calls SetVirtualAddressMap, the firmware relocates the runtime pointers and only the virtual mappings are valid thereafter.

Image entry handoff

The entry point of every EFI image is 

EFI_STATUS EFIAPI efi_main(EFI_HANDLE ImageHandle, EFI_SYSTEM_TABLE *SystemTable);

The firmware (D1b.4) loads the PE32+/COFF image (D1b.1) at a firmware-chosen base, applies the .reloc base relocations (the same R_STACKVM_RELATIVE DIR64 fixups the linker emits), and transfers control to AddressOfEntryPoint with ImageHandle as the first EFIAPI argument and SystemTable as the second. The image's PE Subsystem field selects the entry semantics: EFI_APPLICATION (10) returns to the firmware (or calls BootServices->Exit); EFI_BOOT_SERVICE_DRIVER (11) and EFI_RUNTIME_DRIVER (12) register protocols and return EFI_SUCCESS to stay resident. These ids match the PE writer (pe_file.py / the --subsystem flag).

An ImageHandle exposes EFI_LOADED_IMAGE_PROTOCOL (image base/size, load options, the device it was loaded from), so an application can find its own command line and a kernel EFI-stub can locate the boot device. This is the standardized analogue of the D1 StartupData/SVSR_SDP handoff: under UEFI the kernel obtains memory + cmdline + initrd via boot services and the DTB configuration table rather than reading StartupData directly.

GUID / handle / protocol model

A handle (EFI_HANDLE) is an opaque pointer into a firmware-internal database. Each handle carries a set of protocol interfaces; a protocol is identified by an EFI_GUID and its interface is a struct of EFIAPI function pointers + data. A consumer obtains an interface with HandleProtocol(handle, &Guid, &Interface), OpenProtocol(...), or finds a provider with LocateProtocol(&Guid, NULL, &Interface); a driver publishes one with InstallProtocolInterface. GUIDs are compared by raw 16-byte value. Well-known protocols the StackVM firmware backs (D1b.3) and the devices they map to:

EFI memory-map descriptor

GetMemoryMap(IN OUT UINTN *MapSize, OUT EFI_MEMORY_DESCRIPTOR *Map, OUT UINTN *MapKey, OUT UINTN *DescriptorSize, OUT UINT32 *DescriptorVersion) returns the current map. Each EFI_MEMORY_DESCRIPTOR is 40 bytes:

OffFieldType
0x00TypeUINT32 (EFI_MEMORY_TYPE)
0x04(pad)UINT32
0x08PhysicalStartEFI_PHYSICAL_ADDRESS
0x10VirtualStartEFI_VIRTUAL_ADDRESS
0x18NumberOfPagesUINT64 (4 KiB pages)
0x20AttributeUINT64 (EFI_MEMORY_* caching/permission bits)

Consumers must stride by DescriptorSize, not sizeof(EFI_MEMORY_DESCRIPTOR): the firmware may return a larger descriptor for forward-compatibility (DescriptorVersion = 1). The firmware derives the descriptors from the D1 physical memory map (SVMEM_* region types → EfiConventionalMemory, EfiLoaderData, EfiReservedMemoryType, EfiBootServicesData, …). MapKey is an opaque generation counter that increments whenever the map changes (a pool/page allocation, a protocol install, etc.).

ExitBootServices

ExitBootServices(EFI_HANDLE ImageHandle, UINTN MapKey) hands ownership of memory to the OS and tears down boot services. The required protocol, identical to real UEFI:

  1. Call GetMemoryMap and record MapKey.
  2. Call ExitBootServices(ImageHandle, MapKey).
  3. If it returns EFI_INVALID_PARAMETER the map changed since step 1 (the MapKey is stale); re-fetch the map and retry once — between the two calls the OS must not allocate (allocation changes the key again).

On success: all EFI_BOOT_SERVICES functions become invalid, the firmware stops servicing the boot-time timer event, the firmware's interrupt handlers are removed (the OS owns the ISR table and the D2/D3 controller from here), and only EFI_RUNTIME_SERVICES and the configuration tables (the DTB) remain. The OS is then free to enable its own paging and call SetVirtualAddressMap to virtualise the runtime services.

Events, timers, and TPL

Task Priority Levels (TPL) map directly onto the StackVM per-core interrupt priority mask (FLAGS bits 0–7, see the asynchronous-interrupt-delivery contract / D2). Raising TPL raises the running priority threshold so that lower-priority interrupt sources are held pending; restoring it lowers the threshold and releases them. The four architectural levels:

TPLValueStackVM meaning
TPL_APPLICATION4normal; all events may fire
TPL_CALLBACK8mask callback-level notifies
TPL_NOTIFY16mask signal notifies
TPL_HIGH_LEVEL31interrupts fully masked (FLAGS enable bit effectively off)

Events (CreateEvent/CreateEventEx) carry a type, a notify-TPL, and an optional notify function. The relevant types: EVT_TIMER (0x80000000), EVT_NOTIFY_WAIT (0x00000100), EVT_NOTIFY_SIGNAL (0x00000200), EVT_SIGNAL_EXIT_BOOT_SERVICES (0x00000201). A timer event armed with SetTimer is driven by the D3 programmable interval timer: when INT_TIMER (0x11) fires, the firmware's timer ISR signals the event (subject to D2 enable/priority gating, so a notify never preempts an equal-or-higher TPL). WaitForEvent blocks at TPL_APPLICATION until one of the supplied events is signalled; CheckEvent polls; SignalEvent queues a notify; CloseEvent destroys it. An EVT_SIGNAL_EXIT_BOOT_SERVICES event's notify runs from inside ExitBootServices.

In-VM service dispatch (firmware trap)

The firmware's service-table entries (EFI_BOOT_SERVICES, EFI_RUNTIME_SERVICES, and the protocol interfaces) hold synthetic function pointers that lie outside physical RAM. When a running EFI image executes a CALL to one of them, the firmware run loop (MinimalUefiFirmware.run() in StackVM/uefi.py) sees ip land on a registered service pointer and traps the call instead of fetching bytecode there. This is how a real in-VM EFI image (not just the host test harness) reaches firmware services.

At the trap, the EFIAPI frame the guest's CALL just built is bp == sp pointing at the saved return ip: 

[bp+0]  return ip        [bp+8]  saved bp
[bp+16] arg0, arg1, ...   [bp+16 + 8*arity] caller-reserved EFI_STATUS slot

The firmware reads arity 8-byte argument slots (each service's argument count is tabulated, protocol methods counting their leading This), marshals pointer parameters to/from guest memory, writes the EFI_STATUS into the caller-reserved return slot, and performs the callee RET (restoring ip/bp/sp); the caller then RST_SPs the argument area, exactly as the caller-cleanup convention specifies. Services that transfer control rather than return (StartImage chain-load, Exit/ResetSystem) redirect the VM and skip the return/unwind.

Standardized bootloaders (D1b.5)

With the firmware + in-VM dispatch in place, StackVM supports the two standardized hand-offs that let largely unmodified third-party bootloaders and kernels run:

  • Linux EFI-stub. A kernel built as a PE32+ EFI application (subsystem EFI_APPLICATION) is loaded and entered at efi_main like any EFI app. Its stub calls GetMemoryMap(), records the MapKey, calls ExitBootServices(ImageHandle, MapKey), and continues into the kernel proper — obtaining memory + cmdline + initrd through boot services and the DTB configuration table rather than reading StartupData directly. Launch it with uefi.run_uefi_app() or python -m IsaacCompiler.StackVM uefi kernel.efi.
  • GRUB-style chain-load. An EFI bootloader (e.g. grub.efi) calls LoadImage(BootPolicy, ParentImageHandle, DevicePath, SourceBuffer, SourceSize, &ImageHandle) — from a SourceBuffer it staged, or with no source to load the firmware's default boot image — then StartImage(ImageHandle, …) to transfer control to the loaded kernel. Chain-load does not return to the bootloader.
  • Multiboot2. The format stock GRUB hands off to is supported directly (without UEFI underneath) in StackVM/multiboot2.py: the bootloader parses the kernel's Multiboot2 header, builds the Multiboot2 information (MBI) structure (memory map, command line, modules, framebuffer, EFI tables), and enters the kernel with the Multiboot2 bootloader magic 0x36D76289. StackVM has no general-purpose registers, so the x86 eax = magic; ebx = mbi convention is mapped onto the native handoff: the magic and the MBI physical address are delivered both on the stack as kmain(magic, mbi) (magic at sp, mbi at sp+8) and in the read-only interrupt-argument registers SVSR_INT_ARG0 / SVSR_INT_ARG1. Launch it with multiboot2.boot_multiboot2() or python -m IsaacCompiler.StackVM multiboot2 kernel.bin --module initrd.

Where the firmware lives

This page is the ABI contract, and the Python reference firmware now implements the minimal custom path in StackVM/uefi.py:

  • D1b.1 — the PE32+/COFF container (DONE): the .efi writer/reader, .reloc base relocations (DIR64 over R_STACKVM_RELATIVE), and the readelf/objdump PE views.
  • D1b.3 — the device/firmware substrate (DONE in the Python reference): Simple Text In/Out over the UART (D5)/paravirt console (D4), Block I/O + Simple File System over virtio-blk (D5), the timer/event model over D2/D3, the RTC, NVRAM variable storage, and a framebuffer for Graphics Output.
  • D1b.4 — the minimal custom UEFI firmware itself (DONE in the Python reference): it builds the tables above, loads the EFI image, applies .reloc fixups, and enters efi_main(ImageHandle, SystemTable); it publishes the DTB configuration table (pairing with D1a, skipping ACPI/AML).
  • D1b.5 — standardized bootloaders on top (DONE in the Python reference): the in-VM EFIAPI service trap that lets a real EFI image call firmware services, the Linux EFI-stub hand-off (GetMemoryMap/ExitBootServices), the GRUB-style LoadImage/StartImage chain-load, and the Multiboot2 protocol (StackVM/multiboot2.py).
