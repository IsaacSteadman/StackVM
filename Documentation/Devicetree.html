StackVM Devicetree (FDT) Bindings

This page is the canonical description of the StackVM platform devicetree bindings: the node layout, compatible strings, and property conventions a StackVM machine uses to describe itself to a kernel. It is the hardware-description half of the boot ABI; the boot handoff itself (the struct StartupData pointed at by SVSR_SDP) is described by StackVM/include/stackvm_boot.h, and the MMIO device registers are in StackVM/include/stackvm_mmio.h. The flattened-devicetree (DTB) binary format itself follows the Devicetree Specification v0.4; the read/write core is StackVM/devicetree.py and the reference binding builder is StackVM/dt_bindings.py (build_stackvm_fdt).

1. Why a devicetree

D1 hands a kernel a fixed struct StartupData with the core count, a physical memory map, the initramfs, the kernel command line, and a dtb pointer. The devicetree evolves the hardware description axis toward the arm64/RISC-V model: a thin register/struct handoff plus a self-describing flattened devicetree blob (FDT/DTB) that StartupData.dtb points at. Adding a device then never changes the boot struct — it adds a devicetree node. The two axes (firmware/handoff vs. hardware description) are independent; these bindings apply whether the firmware is the emulator-as-firmware path (D1) or a later UEFI handoff (D1b).

2. The blob (FDT/DTB)

A DTB is a big-endian binary tree: a 40-byte header (magic 0xD00DFEED, totalsize, the offsets/sizes of the structure and strings blocks, the memory-reservation offset, and version/last_comp_version), a memory-reservation block of (address, size) u64 pairs terminated by an all-zero entry, a structure block of 32-bit tokens (FDT_BEGIN_NODE/END_NODE/PROP/NOP/END), and a deduplicated strings block holding the property names. A devicetree cell is a big-endian u32; a u64 is the high cell followed by the low cell. StackVM emits version 17 (last-compatible 16).

3. Address model

StackVM physical addresses are 64-bit and the MMIO aperture lives high (0xFFFF0000+), so the root and the /soc bus declare #address-cells = <2> and #size-cells = <2>. A reg entry is therefore four cells: <base_hi base_lo size_hi size_lo>. The /cpus node is the usual exception: #address-cells = <1>, #size-cells = <0>, so a CPU reg is a single cell holding the core id.

4.2 /memory

A node named memory@<base> with device_type = "memory" and a reg that lists the RAM-backed regions of the D1 memory map (contiguous runs coalesced) as <base size> pairs. The low reserved/firmware guard region below the kernel is not advertised here; the in-use kernel image and bootdata are advertised but carved out under /reserved-memory.

4.3 /reserved-memory

Standard reserved-memory container (#address-cells/#size-cells = <2>, empty ranges). One child per carve-out — kernel@<base> and bootdata@<base> — each with a reg and the no-map flag so the kernel keeps the region out of its allocator.

4.4 /chosen

PropertyMeaning
bootargsthe kernel command line (== StartupData.cmdline)
stdout-pathfull path of the early-console device (the UART, e.g. "/soc/serial@ffff0000")
linux,initrd-startu64 physical base of the initramfs (omitted if none)
linux,initrd-endu64 physical end (base + size) of the initramfs

4.5 /cpus

#address-cells = <1>, #size-cells = <0>, with one cpu@N child per online core (StartupData.core_count). Each carries device_type = "cpu", compatible = "stackvm,cpu", and reg = <N>, where N is the value the core reads from SVSR_CORE_ID (0x0A).

4.6 /soc

A simple-bus (#address-cells/#size-cells = <2>, empty ranges — identity mapping) holding the MMIO devices. Each device node carries a compatible, a reg window matching stackvm_mmio.h, and (for interrupting devices) an interrupts list plus interrupt-parent = <&intc>.

Interrupt controller

interrupt-controller@ffff1000, compatible = "stackvm,intc", with the interrupt-controller flag, #interrupt-cells = <1> (one cell per IRQ line), and a fixed phandle = <1>. It models the D5 MMIO interrupt controller (pending/enable/claim/EOI/route/priority), whose lines are delivered as architectural interrupt vectors per Interrupts.html.

Every window is SVM_MMIO_WINDOW_SIZE (0x1000) bytes. The virtio transports use the standard "virtio,mmio" binding; the device class (block vs. net) is discovered from the transport's device-id register, not the devicetree. A framebuffer (compatible = "simple-framebuffer") is reserved for D1b.3 and is not emitted until that device exists.

5. Reference builder

StackVM.dt_bindings.build_stackvm_fdt(...) emits a binding-conformant tree from a machine description (memory regions, reserved regions, core count, command line, initramfs extent, and a device list that defaults to default_soc_devices()). The companion dt_regions_from_mem_map(mem_map) derives the /memory and /reserved-memory region lists from a D1 boot memory map. The emulator wiring that calls this from the boot path and slims StartupData is D1a.3.

6. Emulator notes

StackVM/devicetree.py is a small libfdt-equivalent: a builder API (FdtNode.set_u32/set_u64/set_string/ set_stringlist/set_cells/set_phandle) and a reader API (FlattenedDeviceTree.from_dtb, get_node(path), and the matching typed get_* accessors). The bindings and the round-trip are covered by tests/test_devicetree.py.
