StackVM Boot ABI

This document is the consolidated boot contract that an out-of-tree kernel port (e.g. arch/stackvm) targets. It pulls together, in one place, every interface a freestanding kernel image depends on between power-on and a running multi-user system:

  1. The StartupData handoff — what the firmware/emulator hands the kernel at entry.
  2. Paravirt hypercall numbers — the phase-1 early-bringup device doorbell.
  3. MMIO device map + IRQ assignments — the phase-2 device window and interrupt lines.
  4. Exception / interrupt numbering — the architectural vector table.
  5. The syscall convention — the user→kernel transition.
  6. The dynamic-linker ABI — for dynamic userspace.

Each section below is a summary plus a pointer to the authoritative source (header, module, or companion document). Where a numeric constant appears here it is mirrored verbatim from the code; the test tests/test_boot_abi_doc.py asserts the two stay in sync, so this page is a checked contract rather than prose that can rot.

0. Boot machine state at kernel entry

The emulator's kernel launch path (StackVM/boot.py, boot_kernel) is the counterpart of the user-program argv path in StackVM/runner.py. It loads a flat kernel image at a page-aligned kernel_base and enters it with:

StateValue at entry
Privilege levelkernel (priv 0); FLAGS bit 8 = 0
MMUoff (VM_DISABLED); physical == virtual
Interruptsmasked (FLAGS bit 14 = 0); priority field = 0xFF
ipkernel_base (start of the loaded image)
sp / bptop of RAM (vm_size), growing down
SVSR_SDP (0x02)physical address of a struct StartupData
SVSR_CORE_ID (0x0A)boot_core_id
SVSR_KERNEL_SP/BP (0x04/0x06)top of RAM

Two firmware/handoff variants build on the same entry state and are documented separately: UEFI / EFIAPI (PE32+ EFI images, including the EFI-stub and Multiboot2 hand-offs) and the devicetree hardware description.

1. The StartupData handoff

SVSR_SDP points at a struct StartupData. All pointers inside it are physical addresses (the MMU is off at entry). A kernel must check magic == SVSD_MAGIC and read only fields within struct_size (forward-compatible append-only growth). Authoritative C definition: StackVM/include/stackvm_boot.h; emulator-side builder/parser: StackVM/boot.py.

struct MemMapEntry is 24 bytes: { u64 base; u64 size; u32 type; u32 reserved; }. The map tiles [0, total_ram) exactly once — contiguous, sorted, non-overlapping; gaps between reserved regions are reported as SVMEM_RAM. Region types:

ValueNameMeaning
1SVMEM_RAMusable RAM, free for the kernel allocator
2SVMEM_RESERVEDreserved firmware/low memory; do not allocate
3SVMEM_KERNELoccupied by the loaded kernel image
4SVMEM_INITRAMFSoccupied by the initramfs blob
5SVMEM_BOOTDATAoccupied by StartupData and its sub-tables

Slim / DTB-authoritative form (SVSD_FLAG_DTB): the loader leaves mem_map/cmdline/initramfs_*/core_count zero and the kernel reads them from the devicetree at dtb instead (arm64/RISC-V style). The initramfs payload stays resident. See Devicetree.html.

2. Paravirt hypercall numbers

Before the MMIO device model is up, a guest kernel reaches host-backed console/block/RTC/entropy services through a kernel-only doorbell: CALL_E with IS_SYS=0, IS_INT=1 and immediate vector INT_PARAVIRT (0x12). This is deliberately separate from CALL_E/SYSCALL (which is a user→kernel transition). User-mode use of the doorbell raises INT_PROTECT_FAULT. Source: StackVM/paravirt.py + StackVM/include/stackvm_boot.h.

The frame at doorbell entry is six little-endian u64s on the guest stack: [sp+0] hypercall number, [sp+8] arg byte count (SVMPV_ARG_BYTES = 32), [sp+16] arg0, [sp+24] arg1, [sp+32] arg2, [sp+40] arg3 (also the return-value slot).

NumberNameArgs → result
0x00CONSOLE_WRITE(buf, len) → bytes written
0x01CONSOLE_READ(buf, len) → bytes read
0x02BLOCK_READ(dev, offset, buf, len) → bytes
0x03BLOCK_WRITE(dev, offset, buf, len) → bytes
0x04RTC_NOW_NS() → Unix time in nanoseconds
0x05ENTROPY(buf, len, flags=0) → bytes

Errors are returned in the result slot as negative-errno u64s: EIO = -5, ENODEV = -19, EINVAL = -22, ENOSPC = -28, ENOSYS = -38.

3. MMIO device map + IRQ assignments

Phase-2 devices live in a physical MMIO window; accesses there dispatch to host-backed device models instead of RAM. Source: StackVM/include/stackvm_mmio.h + StackVM/mmio.py. The base window is SVM_MMIO_BASE = 0xFFFF0000, with 0x1000-byte device slots:

Physical baseDeviceIRQ line
0xFFFF0000UART0 (serial console)SVM_IRQ_UART0 = 1
0xFFFF1000Interrupt controller—
0xFFFF2000RTCSVM_IRQ_RTC = 3
0xFFFF3000virtio-blk0SVM_IRQ_VIRTIO_BLK0 = 2
0xFFFF4000virtio-net0SVM_IRQ_VIRTIO_NET0 = 4
0xFFFF5000simple-framebuffer (regs)—
0xFFFF0000+0x100000framebuffer pixel aperture—

Device IRQ lines are raised into the MMIO interrupt controller (pending/enable/claim/EOI/route/priority registers at SVM_IC_* offsets), which routes an enabled line to an architectural vector — by default INT_HW_IO (0x10) — and delivers it through the asynchronous interrupt gate (FLAGS enable + priority). The UART exposes DATA/STATUS/ IRQ_ENABLE/IRQ_STATUS/IRQ_ACK; virtio devices use the compact virtio-MMIO transport (MAGIC=0x74726976, version 2, device ids: net=1, block=2). Register-level offsets are in stackvm_mmio.h. See also Devicetree.html for how these windows and IRQs are enumerated to the kernel as DT nodes.

The architectural 256-entry vector table is documented in full in Interrupts.html. The boot-relevant vectors:

0x1ETLB_SHOOTDOWN_DONEasync (shootdown completion)

Handlers are looked up in the 16-byte-per-entry ISR table at SVSR_ISR (0x01): [u64 isr_flags][u64 handler_addr]. On entry the processor builds a 48-byte v3 frame on the kernel stack (int_num, error_code, saved_flags, user_bp, user_sp, user_ip) and applies isr_flags; IRET (RET_E with IS_SYS|IS_INT) unwinds it. Carried arguments arrive in the read-only kernel registers SVSR_INT_ARG0..3 (0x0E..0x11); page/protect faults also report the faulting address (see SVSR_PAGE_FAULT_ADDR, 0x0D, and the PAGE_FAULT/PROTECT_FAULT argument columns in Interrupts.html). Asynchronous delivery, enable-gating, priority masking and the NMI path are specified in stack_vm.md ("Asynchronous interrupt delivery"). TLB maintenance / shootdown is specified in TlbShootdown.html and INVTLB.html.

5. Syscall convention

User code enters the kernel with CALL_E using IS_SYS=1 (full instruction reference: CALL_E.html; the return is RET_E.html). The caller pushes, in order, the argument bytes, an 8-byte byte-count num, and the syscall number; the byte after the opcode encodes the syscall-number size class. On the transition the processor switches to the kernel stack, decrements the privilege level, and the handler sees on its stack:

  • syscall number (u64)
  • number of argument bytes passed (u64)
  • the argument bytes copied from the caller's stack
  • saved prev_bp, prev_ip

bp == sp on handler entry. The dispatch target is the kernel syscall entry in SVSR_SYS_FN (0x03); an unrecognised number raises INT_INVAL_SYSCALL (0x0F). This is distinct from the paravirt doorbell in §2, which is the kernel's path to the host, not userspace's path to the kernel.

6. Dynamic-linker ABI

The interchange object/executable format is ELF64 little-endian with machine type EM_STACKVM = 0x5356. Static relocations: R_STACKVM_NONE=0, R_STACKVM_64=1, R_STACKVM_PC64=2, R_STACKVM_RELATIVE=3. Dynamic relocations: R_STACKVM_GLOB_DAT=4, R_STACKVM_JUMP_SLOT=5, R_STACKVM_COPY=6. The full PLT/GOT + loader contract, the DT_* tag set and the -shared/-pie (ET_DYN, DF_1_PIE) image layout are specified in DynamicLinking.html. The UEFI/PE32+ image path (machine IMAGE_FILE_MACHINE_STACKVM = 0x5356, base relocations) is in Uefi.html.

Status: the toolchain emits all of the above (objects, executables, shared/PIE images, dynamic tables). The compiler's -fPIC GOT/PLT code generation and the in-emulator runtime loader are scheduled with the dynamic-userspace milestone; this ABI is the target they build to.
