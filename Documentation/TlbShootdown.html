StackVM TLB & TLB Shootdown

This page is the canonical description of StackVM's translation-lookaside buffer (TLB) and the multi-core TLB-shootdown protocol. The instruction encoding is in INVTLB.html; the interrupt vectors are in Interrupts.html; the relevant system registers are in SYSREG.html.

1. The TLB and address-space identity (no ASID)

StackVM deliberately has no ASID/PCID. Instead, the top-level page-table pointer (TLPTR) is the address-space identity. Each core has exactly two active TLPTRs at any time: its KERNEL_TLPTR (0x08) and USER_TLPTR (0x09). Kernel-space virtual addresses resolve through KERNEL_TLPTR and user-space addresses through USER_TLPTR.

TLB invariant. A core's TLB may only contain entries derived from its two currently-active TLPTRs. Each entry is therefore tagged with the TLPTR it came from.

Auto-flush on switch. Writing KERNEL_TLPTR or USER_TLPTR evicts the TLB entries tagged with the replaced value (unless the same value is still referenced by the other slot). Because KERNEL_TLPTR rarely changes, kernel translations survive context switches — which is the persistence a "global" page bit would provide on an ASID-tagged design, so StackVM needs no global bit. The cost of having no ASID is that the user TLB is dropped on each address-space switch.

A consequence worth stating: StackVM does not map the same kernel pages into every user address space. The kernel has its own TLPTR. Memory genuinely shared between address spaces (user↔user IPC, user↔kernel io_uring) simply appears under more than one TLPTR, and unmapping it requires one shootdown per TLPTR it appears under — which the multi-descriptor request (below) issues in one instruction.

2. Shootdown descriptor and self-filtering

A shootdown is described by one or more 24-byte descriptors:

struct TlbShootdownEntry {
    uint64_t tlptr;        // address-space identity
    uint64_t vaddr_base;   // page-aligned
    uint64_t page_count;   // pages, in the current VM-mode page size
};

Self-filter. A core acts on a descriptor only if descriptor.tlptr == KERNEL_TLPTR || descriptor.tlptr == USER_TLPTR on that core; otherwise it ignores the request. This is safe precisely because of the TLB invariant plus auto-flush: if a TLPTR is not currently active on a core, that core cannot be holding any entries for it (it dropped them when it switched away), and it will rebuild fresh entries from the (now-edited) page tables if it ever switches back.

3. Request shapes: single vs. multi

  • Single (INVTLB_SINGLE): the descriptor (tlptr, vaddr_base, page_count) is passed on the stack. The matching interrupt (request or completion) reports the same three values.
  • Multi (INVTLB_MULTI): a (entry_ptr, num_entries) pair points at an array of descriptors in kernel address space. The matching interrupt reports the same pointer and length. Multi exists to fan a shared page out across all the TLPTRs it lives under in a single request.

4. Completion: SYNC vs. ASYNC

  • SYNC (ASYNC flag clear): the issuing instruction blocks and retires only once the shootdown is complete on all targets.
  • ASYNC (ASYNC flag set): the instruction posts the request and returns immediately. When the shootdown completes, INT_TLB_SHOOTDOWN_DONE is delivered to a nominated done_core (which may be the issuer or any other core), carrying the same descriptor data so the continuation can resume or migrate there.

5. Delivery: hardware broadcast vs. remote-interrupt fallback

  • Broadcast (REMOTE_INT flag clear, recommended): the hardware invalidates the matching entries in the other cores' TLBs without interrupting them. No ISR runs on the targets.
  • Remote-interrupt (REMOTE_INT flag set, documented fallback): the matching cores take INT_TLB_SHOOTDOWN, invalidate the range with INVTLB_LOCAL, and acknowledge with INVTLB_ACK using the handle supplied in the interrupt. The issuer's completion (SYNC retire or ASYNC done-interrupt) fires once all targets have acknowledged.

The ALSO_LOCAL flag additionally invalidates the issuing core's own TLB (a shootdown otherwise targets only other cores).

6. Memory-ordering / coherence contract

The software sequence for changing a live mapping is:

store new PTE
FENCE_STORE              ; make the PTE edit globally visible first
INVTLB_SINGLE/MULTI ...  ; invalidate stale translations
; SYNC retire, or wait for INT_TLB_SHOOTDOWN_DONE
; only now may the freed page be reused
  • Page-table walks may be speculative, so changing a mapping in a way that narrows permissions or changes the output PFN requires break-before-make: invalidate (and complete) before relying on the new mapping. Relaxing permissions may be done lazily; a spurious fault handler must re-check the PTE before reporting an error.
  • Changing a non-leaf PTE requires the INCLUDE_INTERMEDIATE flag so cached intermediate (page-walk) entries are also dropped; leaf edits may use the default leaf-only invalidation.
  • Huge mappings within a range are invalidated as a whole; a range that covers a huge page drops all of its constituent small-page translations.

7. Reserved for the future

INVTLB sub-op codes 0x05+ and flag bits 0x10+ are reserved so that VMID / two-stage (stage-2) translation for hosting a hypervisor can be added without breaking the encoding.

8. Emulator notes

The Python reference emulator (StackVM/PyStackVM.py) implements a consulted per-core TLB, the auto-flush invariant, the self-filter, and a cooperative multi-core bus (MultiCoreController). Because that bus steps cores one at a time, the broadcast path applies invalidations to sibling TLBs synchronously; ASYNC completion is posted to done_core's interrupt mailbox, and SYNC retires immediately after the synchronous broadcast. The C++ core (StackVM/cpp/stack_vm.cpp) implements the consulted TLB and all INVTLB sub-operations for a single core; cross-core broadcast and async completion are handled by the controller in the reference model.
