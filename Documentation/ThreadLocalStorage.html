Thread-Local Storage (TLS) ABI

IsaacCompiler supports the C11 _Thread_local storage-class specifier and its GNU spelling __thread. A thread-local object has thread storage duration: a distinct instance exists per thread, created when the thread starts and destroyed when it ends. This page documents the on-target ABI the compiler emits and that a kernel / dynamic loader is expected to honour. The libc and dynamic loader themselves are out of scope; this page is the contract they target.

Model: static / local-exec

The compiler emits the classic static (local-exec) TLS model. There is no per-object indirection through a GOT or a __tls_get_addr dynamic-resolver call: every thread-local has a fixed, link-time-constant offset within the thread's TLS block. (A general-dynamic model layered on the C3 dynamic-linking ABI can be added later without changing the layout described here.)

The TLS template

All thread-local objects are emitted into a dedicated output section, .tdata. The linker lays this section out contiguously to form the TLS template — the initialisation image that a loader copies into every thread's TLS block. Zero-initialised thread-locals are emitted as explicit zero bytes in the template; a separate .tbss optimisation may be layered on later without changing the generated code.

The linker defines the following symbols describing the template:

Symbol Meaning
__tls_template_start Address of the first byte of the TLS template.
__tls_template_end Address one past the last byte of the template.
__tls_size Size of the template in bytes (the per-thread TLS block size).
__tls_align Required alignment of a thread's TLS block.

The thread pointer: SVSR_TLS_BASE

The per-thread base address is held in the system register TLS_BASE (0x12). It is readable from user mode (TLS-relative loads execute in user code) and written by the kernel / loader on context switch. A thread-local object x is addressed at runtime as: 

&x_runtime = SVSR_TLS_BASE + (&x_in_template - __tls_template_start)

i.e. the object's link-time offset within the template, biased by the current thread's base. The compiler emits this address computation directly in front of every load, store, array-decay or member access of a thread-local; the bytecode sequence (see code_gen/tls.py TlsLink.emit_lea) is: 

LOAD  EA_R_IP, &x                ; absolute template address of x
LOAD  EA_R_IP, __tls_template_start
SUB8                             ; offset = &x - template_start
LOAD  SYSREG, TLS_BASE           ; current thread pointer
ADD8                             ; runtime address in this thread's block

Loader / runtime responsibilities

  1. For each thread, allocate a block of at least __tls_size bytes aligned to __tls_align.
  2. Copy the __tls_size bytes starting at __tls_template_start into the block (this initialises the thread's copies of all .tdata values).
  3. Set SVSR_TLS_BASE to the block's base address before running thread code, and restore it on every context switch.

A single-threaded program with no loader may simply set SVSR_TLS_BASE = __tls_template_start, in which case the template doubles as the live storage for the one thread.

Source-level usage

_Thread_local int errno_like;     /* C11 spelling */
__thread int per_thread_counter;  /* GNU spelling (preprocessed to _Thread_local) */
static __thread int cached;       /* internal linkage, thread storage duration */

The restrict qualifier (and its GNU spellings __restrict / __restrict__) is accepted and parsed but otherwise ignored, as it only constrains aliasing for the optimizer.
